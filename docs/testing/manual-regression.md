# Общая ручная регрессия FBE Next

Действующий незаполненный чек-лист. Сценарии и Binary API сверены с master `975b9d7b` 20 октября 2026 года; это дата редактирования документа, а не выполнения ручных проверок. Все начальные статусы — `NOT RUN`.

## Как проводить и фиксировать прогон

Используйте отдельные тестовые книги и изолированные installed/portable-копии. До отказных сценариев сохраните исходные файлы и контрольные суммы. В одной строке нельзя объединять результаты разных ОС, книг или сборок: для повторения копируйте строку с тем же ID в рабочую запись прогона и указывайте среду. Исходный шаблон не переносит оценки исторических прогонов; они доступны в Git.

Запишите перед прогоном:

- Дату и проверяющего; commit исходников, версию приложения и SHA-256 проверяемого EXE.
- Источник поставки: setup, portable ZIP или собственная сборка; имя/версию артефакта. Отдельно — режим installed/portable и каталог данных.
- Версию и архитектуру Windows, язык ОС/интерфейса, DPI, тему и реальные мониторы.
- FB2/FBD, имя/редакцию тестового документа, исходные SHA-256 вложений и выделение; для скрипта — его имя/параметры и версию API.
- Фактический результат, `PASS` / `FAIL` / `NOT RUN` / `BLOCKED`, причину ограничения и ссылку на лог/скриншот/сохранённый файл.

`PASS` означает выполненный сценарий с подтверждённым ожидаемым результатом; `FAIL` — наблюдаемое расхождение; `NOT RUN` — проверка не выполнялась; `BLOCKED` — зафиксированное препятствие выполнению. Отсутствие доступной Windows 7 или реального DPI-перехода не заменяется успешным тестом на другой среде. Неприменимость к FBD (например, Body отсутствует) отмечайте в замечаниях с причиной, а не как PASS.

Ожидаемое поведение записано заранее; фактические поля до прогона пусты. Автоматический stage3b и статические проверки документации не заполняют эти поля. Внешний известный CI FAIL `test-portable-scripts-infrastructure.ps1` / `PortableToolbarStore.cpp` в этом чек-листе не исправляется и не считается результатом ручной регрессии.

## Минимум перед выпуском

Открытие → редактирование → сохранение → reopen; предыдущая правка → новая операция → Undo/Redo; ZIP; массовая замена; отказ/отмена экспорта; изоляция installed/portable; безопасный диагностический пакет. Затем выполните сценарии затронутой подсистемы, включая Binary API при изменении вложений. Общие build/release-команды ниже — часть подходящего контура, а не требование запускать полный gate после правки документации.

## Пожелания и существующие задачи

Сверка TODO и GitHub Issues выполнена 20 октября 2026 года; состояния ниже не являются результатами тестов.

- Команды закрытия нескольких документов относятся к открытому [#50](https://github.com/sklart/fictionbook-editor-next/issues/50); это план, не обязательный PASS существующего интерфейса.
- Единообразие шрифтов/подсказок относится к [#43](https://github.com/sklart/fictionbook-editor-next/issues/43), локализация FBV/плагинов — к [#2](https://github.com/sklart/fictionbook-editor-next/issues/2). Дубли в [TODO](../todo.md) не добавляются.
- JPEG 2000/WebP и автономный HTML уже имеют закрытые [#21](https://github.com/sklart/fictionbook-editor-next/issues/21) и [#40](https://github.com/sklart/fictionbook-editor-next/issues/40); ниже они проверяются как регрессия соответствующих возможностей, без повторного открытия пожелания.
- Старое пожелание выбора файлов/папки в FBV без аргументов не объявляется реализованным контрактом: текущий FBV получает файлы из командной строки и закрывается при пустом списке. Отдельное продуктовое решение о таком GUI не заменяется тестом с обещанным PASS. Прямой запуск с тестовым FB2 и локализация проверяются ниже.

Контракт: [справочник шести методов](../scripting-api.md#бинарные-объекты-api-130). Адресный автоматический контур — [test-fbe-scripting-stage3b.ps1](../../tools/tests/test-fbe-scripting-stage3b.ps1); он использует отдельную изоляцию и не заменяет наблюдение ручного результата. Сопоставляйте поля JSON и HRESULT, а не только отсутствие исключения. В JScript глобальный JSON может отсутствовать; используйте совместимый разбор только доверенного JSON, возвращённого самим API.

### Подготовка и общие критерии

Подготовьте отдельные валидные FB2 и FBD с PNG/JPEG известного размера (например, 3 × 2), вторым PNG (5 × 4), не-изображением, неиспользуемым binary, обложками title-info/src-title-info. В FB2 добавьте блочное и строчное изображения. Сохраните исходные байты/MIME/ID, ссылки, обложки, XML, выделение, dirty-state, положение savepoint и предыдущие Undo/Redo. Исходные данные и результаты экспорта держите в отдельном временном каталоге; не меняйте комплектные runtime/Scripts и контрольные JSON ради подготовки.

Нужны файлы с кириллицей/пробелами, PNG/JPEG, PDF с корректным заголовком, произвольный binary с явным application/octet-stream, отсутствующий путь, пустой/повреждённый/заблокированный файл и файл >64 МиБ. Для граничных проверок подготовьте допустимый файл ровно 64 МиБ и изображения у/за пределами 16384 по оси и 32 миллионов пикселей. Это входы нового прогона; их создание и проверка здесь не выполнялись.

Для каждой успешной Add/Replace/Remove: сравните состояние до/после → один Undo → один Redo → повторный Undo; проверьте исходные байты, MIME, ID, позиции изображений, ссылки, обложки и выделение. Предыдущая история сохраняется; новая успешная правка штатно заменяет ветку Redo. Отказ должен оставить книгу, dirty/savepoint и обе истории прежними, закрыть временные группы; следующий обычный ввод и Undo/Redo должны работать.

GetBinaryInfo, GenerateUniqueBinaryId и SaveAllBinaries не меняют книгу, выделение, dirty/savepoint или Undo/Redo; экспорт изменяет только явно выбранные внешние файлы. Для проверки сохранённых binary декодируйте base64 из сохранённого XML и сравните исходные байты/хеши, а не переносы строк base64 или весь сериализованный XML.

Контролируемые COM/память/регистрация-Undo отказы воспроизводятся только в изолированной тестовой среде с документированными механизмами stage3b. Если подходящей тестовой сборки нет, оставьте сценарий NOT RUN либо запишите BLOCKED с причиной; не подменяйте его обычным успешным вызовом и не включайте fault injection в рабочей копии.

## Итог прогона и приёмка

Запишите раздельные PASS/FAIL/NOT RUN/BLOCKED и нерешённые дефекты; для каждого FAIL приложите вход, действие, ожидаемое/полученное, среду, commit/SHA EXE и артефакт. Общий результат не вычисляйте как процент заполненных строк: важны критичность и фактическое покрытие комбинаций. После исправления повторяйте затронутые сценарии и сохраняйте ссылку на исходный дефект, не переписывая его как исторический PASS.

Для Binary API приёмка требует подтверждённых байтов/MIME/ID, ссылок и обложек, атомарного отказа, правильного одиночного Undo/Redo, Save/Reopen и отказа Source; пропущенный критический контур явно остаётся непроверенным. Результат автоматического stage3b записывается отдельно и не превращает BAPI-строки в выполненную ручную проверку.

# Диагностика порядка native и custom Undo units — 28.10.2026

**Результат: INCONCLUSIVE / NO-GO.** Установлено, что конфликтующая операция не является ранее существовавшей одноимённой операцией: это отдельный COM-объект, появившийся во время внешнего Undo custom unit. Публичный `IOleUndoManager` отказывает в перечислении обоих стеков внутри `Do`, поэтому по этим данным нельзя определить, появилась ли операция непосредственно при DOM-мутации, при `Add`, или при завершении внешнего Undo. Происхождение и точный момент регистрации не доказаны; production-кандидата нет.

## Метод и карта истории

Проба получает настоящий manager через сервис документа. Регистрируются обе последовательности `EnumUndoable`/`EnumRedoable`, `GetUnitType`, `GetDescription`, контрольные точки DOM, FNV-1a нормализованного DOM, selection, HRESULT, вызовы `Do`, `Add`, `OnNextAdd`, `GetOpenParentState`. Внешний порядок строк соответствует порядку наблюдения. Нативные `IUnknown` удерживаются до завершения пробы и получают номера `held-N`, что предотвращает повторное использование адреса в пределах наблюдения; собственный unit удерживается вызывающим кодом и обозначен `custom-0`. Это верхнеуровневые units, а не полный перехват внутренних действий MSHTML. Удержание ссылок является вмешательством наблюдателя; прежняя проба без него воспроизводила тот же текстовый отказ.

`GetLastUndoDescription` и `GetLastRedoDescription` отдельно не инструментированы: описания получены у перечисленных units. Числового поля sequence нет, порядок задаётся порядком строк. Внутреннее состояние тестового unit без DOM не переключается. Поэтому инструментирование и матрица не покрывают все пункты ТЗ.

В окончательной сборке, текстовая мутация `innerHTML`:

|---|---|

## Аудит custom unit и следующий шаг

Экспериментальный unit использует один объект для обратной регистрации `Add(this)`; для основного варианта Add происходит после мутации, HRESULT фиксируется. Сохранён живой элемент, но не доказывается стабильность дочерних DOM-узлов. `m_doing` запрещает повторный вход, COM-ссылки принадлежат `CComPtr`/smart pointer, ссылки из наблюдателя освобождаются при `DetachReport`. Успешный Add сам по себе не гарантирует сохранность внешней истории: текстовый сценарий нарушает порядок. Путь отказа **не является атомарным**: при ошибке Add после мутации нет подтверждённого отката DOM и истории. Инъекции такой ошибки не выполнены. Не использовать этот класс как production-реализацию.

Согласующий кандидат не проверялся: до локализации момента создания операции это был бы необоснованный перебор. Следующий адресный шаг — test-only прокси вокруг переданного в `Do` manager, журналирующий вызовы `Add` с удержанными identity и делегированием без изменения порядка; отдельно проверить, получает ли MSHTML тот же manager или обходит прокси. Параллельно построить обратимый тест одного реально идентифицированного текстового узла с независимым снимком соседних узлов. Если MSHTML добавляет операцию через другой внутренний путь, одной публичной прокси недостаточно: требуется наблюдение на границе документа/менеджера или отладочная трасса, без `Enable(FALSE)` и очистки истории. Это гипотеза следующей проверки, не доказанная архитектурная необходимость глобального адаптера.

При возможном изменении архитектуры потребуется оценить обычный ввод, Copy/Paste, Clone, Merge, Cite/Poem и Table: все они могут сочетать native и прикладные операции и потерять порядок или savepoint. Production Split, общий manager, ввод и dirty не менялись.

## Контроль текста и savepoint

Тест теперь отдельно сообщает TEXT_UNDO, TEXT_REDO, HISTORY_ORDER, CARET_RESTORE, SELECTION_RESTORE, XML_INTEGRITY и DIRTY_SAVEPOINT; dirty не маскирует результат текста. В контрольной матрице восемь текстовых вариантов прошли, все восемь dirty-проверок не прошли. Последовательные Q и X могут объединяться; с перемещением каретки получены независимые Undo/Redo и точные `Qtail → QXtail`. Контроль без промежуточного XML-наблюдения подтверждает результат. Вложенная обработка сообщений сама по себе не доказывает разделения полных пользовательских событий; реальный ручной клавиатурный ввод отдельно не проверен.

| Сценарий после реального Save | Наблюдение |
|---|---|
| Q → Undo / Redo | Синтетические DOM и XML после Undo совпадают с сохранёнными, но DocChanged остаётся true; текущая версия 1687 против сохранённой 1685 |
| Форматирование → Undo | DOM и модель возвращены, dirty остаётся true; версия 1687 против 1685 |
| Description → Undo | Модель возвращена; версия тела 1685 не меняется, `IsFormChanged()` остаётся true |
| Save → Q → Save → Undo → Redo | Redo возвращает сохранённую модель, dirty остаётся true; версии 1688 и 1686 |
| Реальный Paste → Undo → Redo | Отдельный сценарий успешно проверил dirty и recovery: после Paste dirty, после Undo clean, после Redo dirty. Перед Paste тест отдельно вызывает MarkDocCP |
| Изменение binary → Undo | NOT RUN; нельзя переносить выводы о теле на binary storage |

Текущая реализация `DocChanged` учитывает отличие версии тела или `IsFormChanged`. `RestoreCleanIfBodyMatches` в обычном вводе не выполняет сверку, пока не установлен специализированный флаг `m_reconcilePasteHistoryClean`; у Paste есть отдельный путь сверки. `DocRelChanged` использует отдельную recovery-точку; обычный Save не следует считать доказательством её сброса. Совпадение XML здесь проверено на синтетической модели и не является универсальным доказательством побайтового совпадения файлов.

Политика A (версия редактора) объясняет часть наблюдений, но специальные Paste и sticky form показывают, что единая фактическая политика не сведена к ней. Политика B (подтверждённый savepoint) могла бы снимать dirty после Undo, однако должна отдельно учитывать Description, binary, переходы Source/Body, recovery и составную историю. Без отдельного решения и проверок выбирать политику и менять production нельзя; сравнение всей книги на каждое нажатие и безусловный MarkSavePoint при Undo недопустимы.

## Минимальная интерференция истории

Настоящий MSHTML/OLE, изолированные синтетические документы. Q и X разделены подтверждённой границей. В таблице текст и dirty проверяются независимо.

| Вариант | Текст и порядок |
|---|---|
| B1 native | PASS, Q и X отменяются и восстанавливаются по порядку |
| B2 пустой custom | PASS; dirty FAIL отдельно |
| B3 обратимое изменение атрибута | PASS; dirty FAIL отдельно |
| B4 локальный текстовый узел | FAIL: после Undo custom перед ожидаемым Redo X появляется дополнительный native unit «Действие с текстом»; следующий Redo не возвращает X, но текст ещё `Qtail` |
| B5 прежний структурный unit | FAIL: после Redo custom текст ещё `Qtail`; следующий native Redo исполняет дополнительное «Действие с текстом» вместо ожидающего «Ввод», и текст становится `l` |

В B4 установка эквивалентного `innerHTML` локального абзаца внутри `Do` достаточна для нарушения порядка без структурного Split. В B5 первая потеря символов происходит **после** возвращения из custom `Do`, при следующем нативном Redo, HRESULT успешен. Это локализует наблюдаемую интерференцию в дополнительном native unit и порядке истории; точный внутренний механизм и минимальные условия именно превращения `Qtail → l` не доказаны. Создание свежей каретки перед Redo не устранило ни лишний unit, ни повреждение в B5; это не исключает влияния других состояний выделения. Логируемые значения указателей являются диагностическими адресами интерфейсов и не доказывают постоянство или устаревание COM identity. Состояние parent в журнале не является полным состоянием Undo Manager.

Это RED для текстового и структурного вариантов, GREEN только для пустого и атрибутного контроля. Новый структурный прототип по этапу D не запускался: B4 не проходит требование сохранения истории. B5 — воспроизведение прежнего отклонённого прототипа для диагностики.

## Каретка после Split → Undo → X

Во всех четырёх опытах после Undo исходная секция восстановлена, но соседняя правая секция остаётся с тем же ID. Без вмешательства X попадает в правую секцию (`Xiddle`). Старый сохранённый `IHTMLTxtRange` направляет ввод в левую, но получается `MX` вместо `MXiddle`: часть исходного текста потеряна. Сохранённый `IMarkupPointer` и новый диапазон в актуальном DOM дали `MXiddle` в левой секции, но дубликат справа сохранился. Таким образом оставшаяся правая секция и сохранившееся в ней выделение объясняют наблюдаемый ввод справа; восстановление позиции не восстанавливает структуру. Эти результаты не доказывают безопасность старого pointer для других DOM-преобразований.

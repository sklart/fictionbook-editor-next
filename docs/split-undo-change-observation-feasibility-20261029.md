# Наблюдение изменений MSHTML и пригодность для истории — 29.10.2026

**INCONCLUSIVE.** Отдельный `IHTMLChangeSink` наблюдал пять проверенных текстовых/структурных мутаций после обработки сообщений; три изменения атрибутов не породили уведомления в ограниченном экспериментальном окне. Полнота покрытия, исходное состояние и границы транзакций не доказаны, поэтому `OBSERVATION_FEASIBLE` и `PARTIAL GO` не присваиваются и общий Undo Manager не реализуется.

Исторический вопрос остаётся неразрешённым; эта наблюдательная проверка не зависит от предположения об унаследованном дефекте. Исходная ветка `codex/fbe-undo-architecture-feasibility`, начальный HEAD `edb32ba6bf38260ab7ec99553a3c7b89eb845551`. Test-only код добавляет отдельную регистрацию и не меняет production Split или Undo. ## Механизм

В существующем редакторе `CFBEView::RangeSink::raw_Notify()` направляет уведомление в `EditorChanged(RANGE_SINK)`; `GetChangedNode()` читает и очищает dirty range по штатному cookie. Проба получает `IMarkupContainer2` из того же документа, регистрирует отдельный `CTestDirtyRangeSink` и отдельный cookie через `RegisterForDirtyRange`, читает только **свой** диапазон и снимает регистрацию. [Документация Microsoft](https://learn.microsoft.com/en-us/previous-versions/windows/internet-explorer/ie-developer/platform-apis/aa703629%28v%3Dvs.85%29) описывает cookie как идентификатор конкретного диапазона. Штатный cookie дерева не передаётся в тестовую очистку.

В одной синтетической книге и одном изолированном процессе последовательно выполняются восемь JS-мутаций. Фиксируются DOM до и после, `GetVersionNumber`, число вызовов sink сразу после возврата `execScript`, после вложенной обработки очереди до собственного контрольного `PostThreadMessage`, после дополнительного `MsgWaitForMultipleObjectsEx` до 100 мс, `GetAndClearDirtyRange` и scope концов. Никакого `Sleep` на UI-потоке нет. Если сообщения уже готовы, ожидание может завершиться раньше 100 мс. Отдельный выход из *внешнего* Windows-сообщения, полноценный idle и гарантированное полное окно не доказаны; вызов Notify внутри самого скрипта отдельно не перехватывался, счётчик сразу после его возврата лишь задаёт верхнюю границу.

| Мутация | Notify сразу / после контрольного сообщения / после дополнительной обработки | Версия до → после | Dirty range и ограничение |
|---|---|---|---|
| `nodeValue` | 0 / 1 / 1 | 1688 → 1691 | S_OK, P/P |
| `innerHTML` | 1 / 2 / 2 | 1691 → 1693 | S_OK, P/P |
| `appendChild` | 2 / 3 / 3 | 1693 → 1694 | S_OK, DIV/DIV |
| `insertBefore` | 3 / 4 / 4 | 1694 → 1695 | S_OK, DIV/DIV |
| `removeChild` | 4 / 5 / 5 | 1695 → 1696 | S_OK, DIV/DIV |
| `id` | 5 / 5 / 5 | 1696 → 1697 | S_OK, scope не получен |
| `href` | 5 / 5 / 5 | 1697 → 1697 | S_OK, scope не получен |
| два `title` подряд | 5 / 5 / 5 | 1697 → 1697 | S_OK, scope не получен |

Счётчики накопительные; для первых пяти прирост произошёл между возвратом скрипта и снятием снимка после обработки сообщений. Точность начала/конца диапазона в символах и факт вызова штатного `EditorChanged` отдельно не измерялись. `S_OK` при пустом scope не доказывает отсутствия внутренних событий. Это один процесс, одна последовательность и один host/MSHTML; нельзя переносить результат на все варианты атрибутов, IME, плагины и прочие среды.

Первая попытка остановилась на JS-ошибке: ID ссылки отсутствовал после преобразования FB2; собственный тестовый процесс завершён вручную. Исправленная попытка нашла ссылку по положению DOM и отработала восемь изменений. Лог первой попытки сохранён и не классифицируется как воспроизведённая ошибка редактора. Предыдущее исследование `oninput`/`onpropertychange` не повторено с полным внешним message loop; результат тестового change sink не равнозначен доказательству доставки этих JS-событий.

## Достаточность для Undo

| Признак | Состояние |
|---|---|
| DETECTED | Для первых пяти — обнаружено отдельным sink в этой последовательности; для трёх атрибутных сценариев прирост не наблюдался в ограниченном окне |
| AREA_KNOWN | Только конечные scope P/P или DIV/DIV; точные границы и достаточность для всей операции INCONCLUSIVE |
| PRESTATE_AVAILABLE | Отдельные до/после снимки сделаны тестом; сам `raw_Notify` и этот dirty-range вывод не передают доказанный исходный фрагмент. Доступность реального обратимого prestate не доказана |
| TRANSACTION_BOUNDARY_KNOWN | INCONCLUSIVE: нет доказанного соответствия одного уведомления одной пользовательской или скриптовой операции |
| REVERSIBLE | NOT RUN: уведомление и снимки не использовались для отмены/повтора пользовательских изменений |

[Microsoft описывает `CreateChangeLog`](https://learn.microsoft.com/en-us/previous-versions/windows/internet-explorer/ie-developer/platform-apis/aa703624%28v%3Dvs.85%29) с forward/backward данными и отдельным sink как возможную область исследования. Его доступность в данном host, реальные данные, покрытие атрибутов и сохранность смешанной истории **не проверялись**; документация не является runtime PASS.

## Скрипты и архитектура

Исходники содержат штатный маршрут `RunScript` и `BeginUndoUnit`/`EndUndoUnit`, но скрипты также напрямую изменяют DOM. Предлагаемый `Script Begin → Prestate → Execution → Poststate → End` может охватывать только подтверждённые синхронные входы; полнота, асинхронные действия, сторонние плагины, исключения, наблюдение prestate и сохранение существующего COM ABI не проверены. Нет оснований называть этот маршрут управляемой обратимой транзакцией или присваивать PARTIAL GO.

Следующие самостоятельные эксперименты: в отдельном процессе с полноценным внешним циклом сообщений и точными временными метками повторить каждое изменение отдельно, включая UI и IME; затем проверить `CreateChangeLog` и данные forward/backward без потребления штатного dirty cookie. Для управляемого скриптового контура независимо проверить непосредственные и отложенные DOM-правки, исключения и плагины. Только после доказательства обнаружения, prestate и границ операций рассматривать Q → Split → X.

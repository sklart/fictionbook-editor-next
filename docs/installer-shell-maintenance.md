# Обслуживание системной интеграции установщика

## Сборка из подготовленных stages

Основная команда — `tools/build/build-installer.ps1`; её используют BAT
`packaging/nsis/Installer/MakeInstaller.bat` и `create-release.ps1`:

```powershell
.\tools\build\build-installer.ps1 -CoreDirectory out\stage\Core -IntegrationDirectory out\stage\Integration
```

Команда проверяет stages, формирует input и вычисляет SHA-256 именно из него.
NSIS независимо сверяет три хеша с DLL и схемой. Отсутствующие stages,
пустые файлы и неверные хеши останавливают сборку. `-OutputDirectory` и
`-OutputFile` позволяют задать отдельные каталоги. Полная сборка редактора
для пересборки setup из готовых stages не нужна.

## Причины исправления

Раньше основной раздел setup обнулял маркеры до обновления обработчика,
резервные копии удалялись до регистрации новой версии, а новый `uninst.exe`
сравнивал старую интеграцию со встроенными новыми SHA-256. Неудачное обновление
могло потерять состояние и возможность удаления. Удаление файлов не проверялось
достаточно строго: занятая DLL могла остаться без сведений о владельце.

## Порядок обновления

`manage-shell-integration.ps1` выполняет операцию `Update`, `Remove`, `Inspect`
или `Recover`. Общие функции находятся в `shell-integration-lifecycle.ps1`.
Операции сериализуются эксклюзивным файловым замком в защищённом Common Files.

1. NSIS сохраняет прежние `InstallLocation`, `PropertyHandlerInstalled` и
   `SystemIntegrationInstalled`. Основной раздел сохраняет прежние маркеры,
   пока помощник не определит фактическое состояние. При снятии выбора
   компонента выполняется `Remove`, в том числе при тихом обновлении.
2. В защищённый уникальный каталог
   `Common Files\FictionBook Editor Next\Maintenance\<сеанс>` извлекаются
   помощники и новый payload. Они не перезаписывают помощники другой установки.
   Старые маркеры записываются в `Previous.ini`, результат — в `Status.ini`.
3. Проверяются владелец, фактические хеши, CLSID, записи расширения и пути схемы.
   Чужие регистрации и файлы без подтверждённого владельца сохраняются.
4. В `Shell\InstalledState.clixml` сохраняется описание фактически установленного
   пакета. В `Shell\State` создаются резервные копии DLL, схемы, `Owner.ini`,
   установленного состояния и журнал `Transaction.clixml`. Журнал содержит
   прежние маркеры/каталог, точные значения и типы пяти деревьев COM/расширения,
   метаданные FictionBook.2 и зарегистрированные пути/хеши схемы.
5. Проверяются три новых хеша, заменяются файлы. Только после готовности файлов
   начинается переход схемы и COM. Ошибка возвращает прежние файлы, реестр,
   схему и `Owner.ini`. Старая DLL при восстановлении не загружается: ключи
   восстанавливаются из снимка, схема — через системный API.
6. Новые `Owner.ini`, установленное состояние и маркер `1` подтверждаются
   после проверки новой COM-регистрации и схемы. Затем удаляются резервные копии.
   Повторный запуск с теми же файлами и полной регистрацией не регистрирует их снова.

Деинсталлятор использует установленное состояние/проверенный старый `Owner.ini`,
а не SHA нового пакета, встроенные в `uninst.exe`. Поэтому он может удалить
старый обработчик после неудачного обновления Core.

При миграции из известных каталогов ProgramData отсутствие `Owner.ini`
допускается только с прежним маркером компонента и полной регистрацией точно
на известную старую DLL. Старые DLL не загружаются и не удаляются: они сохраняются
для безопасного отката. После успешного перехода активны DLL и схема в Common Files.

## Результаты и действия пользователя

| Результат | Значение и дальнейшее действие |
|---|---|
| `ok` | Операция подтверждена. `PropertyHandlerInstalled` отражает действующую регистрацию. |
| `pending / FILES_IN_USE` | Прежняя интеграция сохранена. Закрыть Проводник либо перезагрузить Windows и повторить setup. |
| `pending / CLEANUP_PENDING` | Регистрация снята, но файлы ещё заняты. Сохранены владелец, запись очистки, помощники и `uninst.exe`; повторить удаление после освобождения файлов. |
| `pending / BACKUP_CLEANUP_PENDING` | Новая регистрация подтверждена, остатки резервной копии требуют повторного запуска. |
| `skipped / FOREIGN_*` | Чужой пакет/регистрация сохранены. Не удалять общие файлы вручную. |
| `error / UPDATE_FAILED` | Новая операция не завершилась; прежнее состояние восстановлено либо изменений не было. Причина есть в журнале. |
| `error / RECOVERY_REQUIRED` | Прерванная операция либо ошибка отката. Снимок сохранён; автоматическая повторная регистрация запрещена до восстановления. |

`ShellCleanupPending` и `ShellRecoveryPending` хранятся рядом с uninstall-записью.
При незавершённой операции `SystemIntegrationInstalled` сохраняет необходимость
обслуживания; после снятия COM `PropertyHandlerInstalled=0`, даже если очистка
файлов ещё ожидается. Setup возвращает `3010` для pending, `2` для skipped и `1`
для error; эти результаты не считаются успешной установкой интеграции.
Статус `ok` при ненулевом коде завершения помощника отклоняется.

Удаление проверяет каждый файл. `Owner.ini` и сведения об установленном пакете
удаляются последними. Отсутствующие после частичной очистки файлы допускаются;
изменившиеся хеши или новая регистрация запрещают продолжение удаления.
Безусловное `Delete /REBOOTOK` для общих DLL не используется.

## Явное восстановление

При `RECOVERY_REQUIRED` сохранить `Shell\State` и каталог Maintenance из журнала.
Запустить от администратора **нативный Windows PowerShell**: на x64 Windows
64-разрядный, на x86 Windows — 32-разрядный. Пример для x64 Windows:

```powershell
& "$env:WINDIR\System32\WindowsPowerShell\v1.0\powershell.exe" -NoProfile -ExecutionPolicy Bypass `
  -File 'C:\Program Files (x86)\Common Files\FictionBook Editor Next\Maintenance\<сеанс>\manage-shell-integration.ps1' `
  -Operation Recover -InstallationDirectory '<каталог установки FBE>'
```

Из 32-разрядного процесса x64 Windows используется `Sysnative` вместо `System32`.
Путь Common Files зависит от ОС. Каталог установки должен совпадать с Owner/снимком.
Помощник повторно проверяет принадлежность, пути и хеши резервных копий.
После `ok / RECOVERED` повторить setup или удаление. При `CLEANUP_PENDING`
повторить именно удаление; `Recover` не возвращает уже снятую регистрацию.
Каталоги Maintenance сохраняют диагностику сеансов и средства восстановления.

## Совместимость

Помощники используют синтаксис Windows PowerShell 2.0 и API .NET 2.0/3.5.
Реестр открывается в нативном представлении процесса; COM и schema helpers
перезапускаются в Windows PowerShell нужной разрядности. Статусы — UTF-16 с BOM,
скрипты — UTF-8 с BOM; пути Unicode не преобразуются в ANSI. PowerShell 7 при
установке не требуется. На Windows 7 сохраняются обычные ограничения Win32
на длину пути. Reparse points в путях payload/снимка отклоняются.

## Краткие проверки 15.10.2026

- `test-nsis-shell-lifecycle.ps1`: настоящие файловые операции и блокировки;
  снимки/восстановление реестра в изолированной ветке HKCU. Вызовы COM/schema
  заменены контролируемыми операциями. Проверены обновление и повторный запуск,
  частичная ошибка COM, ошибка схемы, точный откат Owner и значений разных типов,
  отказ восстановления при подменённой резервной копии, занятая DLL, снятие компонента, старый пакет с новым набором встроенных хешей,
  занятые DLL/помощник при удалении, повторная очистка без повторной регистрации,
  чужие файлы/владелец/COM, первая установка, незавершённый откат и явное
  восстановление из сохранённого XML, откат при ошибке записи состояния удаления,
  занятая резервная копия после подтверждённой регистрации, миграция ProgramData
  и её откат. Передача параметров/статуса файловому помощнику дополнительно
  проверена через настоящий дочерний Windows PowerShell.
- `test-nsis-shell-maintenance.ps1`: реальные register/unregister helper-функции
  в HKCU, отказ при чужом владельце/хеше/COM и ошибке схемы, настоящий откат
  файлов и проверка содержимого NSIS input. Обе проверки пройдены в PowerShell 7
  и Windows PowerShell 5.1.
- Контракты package layout, ownership-safe uninstall, toolchain, deployment modes,
  согласованности shell-строк и локализации NSIS; scope-пробы Current User /
  All Users / Portable. Setup собран из готовых Core и обновлённого Integration.
- UAC/IPC, редактор и зависимости не изменялись. Полная сборка редактора,
  release gate и полная CI-матрица не запускались.

На машине имеются действующие системные обработчики FBE: их HKLM-регистрация
не изменялась. Изолированные проверки не подтверждают настоящую установку
COM/schema, загрузку DLL Проводником, очистку после перезагрузки, UAC под другой
учётной записью и работу Windows 7 SP1 с исходными PowerShell 2.0/.NET 3.5.
Эти сценарии требуют чистой Windows VM.

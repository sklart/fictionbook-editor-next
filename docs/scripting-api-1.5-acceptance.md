# Приёмка scripting API 1.5.0 — issue #45

Дата аудита: 21 октября 2026 года. Исходная точка задания: `713e2661ba86d2cc26cdf172aaa63617ee921431`; проверяемая реализация: `7de47ab3262b44b510713533b7ed81ea1529c191`.

**Решение: KEEP OPEN.** Публичный контракт содержит 104 метода, API 1.5.0; обязательная проверка разных DPI и локалей из раздела 18 исходного issue ещё не выполнена. Исходный тайм-аут 3Г installed/FBD/UTF-16 разобран отдельно в #69: устранена зависимость времени API-теста от полного стартового каталога скриптов, новый адресный контур проходит (см. дополнение ниже). Отдельная задача не превращает невыполненное требование в DONE. Требуется явно согласовать границы отложенных возможностей разделов 4–5. Независимые сбои общего Build не являются доказательством дефекта API, но общий Build нельзя объявлять успешным.

## Отложенные возможности и самостоятельные задачи

- **DEFERRED:** ProcessPendingUiEvents, безопасный yield и отложенные обновления пакетного режима — [#65](https://github.com/sklart/fictionbook-editor-next/issues/65), связано с производительностью [#41](https://github.com/sklart/fictionbook-editor-next/issues/41) и [#59](https://github.com/sklart/fictionbook-editor-next/issues/59). До определения защиты от повторного входа метод не публикуется.
- Автоматический откат произвольных DOM-изменений не поддерживается. BeginDocumentUpdate объединяет штатный Undo и восстанавливает временные состояния редактора; это не транзакция и не обещание восстановить любой DOM. Отдельный новый метод исключительно ради формального совпадения с предложением не добавляется.
- Матрица приёмки DPI/локалей и подтверждение платформ — [#66](https://github.com/sklart/fictionbook-editor-next/issues/66). Windows 7 SP1, разные DPI и локали: **NOT RUN**. Это оставшийся критерий приёмки #45.
- Тайм-аут адресного installed/FBD/UTF-16 — [#69](https://github.com/sklart/fictionbook-editor-next/issues/69). Новый контур проходит после изоляции стартового каталога скриптов; подробности и границы подтверждения приведены ниже. Это не закрывает #65 и #66.
- Отдельный LoadBinaryFromFile, возвращающий сырые данные без добавления в книгу, отсутствует. Для заявленных операций импорта/замены/экспорта достаточно существующего бинарного API; независимый сценарий для ещё одного метода не установлен.

## Дополнение по #69: изоляция стартового каталога

На чистом снимке `e5b1279e41ff2b13254406925e8d1a414ff43666` добавлены временные точки с GetTickCount64 и немедленным FlushFileBuffers: старт/режим, загрузка настроек, вход/выход Initialize и Discover, вход в сценарий и первый JScript. Существующие коды XML/DOM-загрузчика также записывались с немедленным сбросом: чтение/разбор XML, преобразование Body/Description и binary. Записывались только коды этапов, без путей, XML и бинарного содержимого. Временные вставки не входят в коммит и не изменяют API.

Исходный тайм-аут на этом снимке **не воспроизвёлся**: все четыре случая прошли и до изменения теста. Однако обнаружена существенная инфраструктурная зависимость: seed не задавал ScriptsFolder, и перед API-сценарием обычный запуск обнаруживал и загружал весь каталог Scripts сборочного runtime (980 JS в диагностическом runtime). Initialize занимал 37–41 секунду, а сам контур 3Г — 1,5–4,3 секунды. Это расходует большую часть общего лимита процесса независимо от формата и кодировки; работа полного комплекта скриптов не является предметом этого теста. Историческое прерывание после P100 само по себе не доказывает дефект FBD или UTF-16 и не устанавливает, на каком конкретном скрипте был исчерпан лимит.

Исправление ограничено инфраструктурой `test-fbe-scripting-stage3d.ps1`: в изолированном профиле явно задан отдельный каталог с копией текущего stage3d.js; CheckScriptsOnStartup=true. Сохраняются обычные Discover/Initialize, реальная загрузка JScript и все проверки API. Каталог отделён от намеренного junction source-dir, используемого проверкой файловых псевдонимов. Пользовательские/комплектные JS не менялись; лимит Wait-IsolatedFbeProcess остался **60 секунд**.

На одном диагностическом EXE (SHA-256 `24EBF255D7F8DDCBF07607B8DE517ABEDE82075553437EA204618C11609F3D9B`) выполнено по одному сравнительному прогону каждого сочетания до и после исправления:

| Режим / документ / вход | Процесс до, с | Процесс после, с | Initialize до → после, мс | Итог после |
|---|---:|---:|---:|---|
| portable / FBD / UTF-16 | 46,922 | 3,875 | 39891 → 78 | PASS |
| installed / FBD / UTF-8 | 43,172 | 3,969 | 37078 → 63 | PASS |
| installed / FB2 / UTF-16 | 48,359 | 4,750 | 41015 → 62 | PASS |
| installed / FBD / UTF-16 | 43,141 | 4,093 | 39125 → 79 | PASS |

Это время самого FBE по монотонным точкам, без копирования runtime и удаления изолированного профиля. Полное время исправленного PowerShell-сценария — 7,0–7,8 секунды. Это единичная адресная сравнительная проверка, а не бенчмарк или гарантия времени на любой машине.

Во всех четырёх случаях получен result=PASS: независимая копия и защита от перезаписи/псевдонимов; текущий Source, UTF-16 BOM и UTF-8/декларации; повторное открытие в FBE; точные байты binary и ссылки; неизменность dirty-state/выделения/Undo/Redo при read-only операциях; очистка профиля, junction и временных файлов. Зависимость от полного каталога удалена; специфического дефекта сочетания installed/FBD/UTF-16 не обнаружено.

Дополнительно выполнен один installed/FBD/UTF-16 на обычной, без временных вставок, Release Win32 сборке `/W4 /WX` без предупреждений: **PASS**, 16 фаз и result=PASS. Native-исходники — `4ee48e6f8cbb6c7da36b83d8e0079312acd0edc9`, SHA-256 EXE `EE97C564D42287CDD17D954C41924EC2618C6C1A3603D4AC9A50C38B9EA2FDC9`. Runtime typelib/FUNCDESC — PASS, IDL и публичный диспетчер не менялись. В существующий CI-контур 1.5 добавлено именно сочетание installed/FBD/UTF-16: прежний UTF-16 вызов покрывал только portable/FB2.

Граница вывода: измеренная зависимость от полного каталога устранена, адресная приёмка проходит. Причина единственного исторического превышения 60 секунд не установлена с точностью до конкретной операции/скрипта, поскольку исходный FAIL на e5b1279e не повторился. Поэтому это не доказательство устранения произвольного зависания редактора; #69 нельзя закрывать только на основании сокращения времени запуска. #45 остаётся открытым также по #65/#66. Старый опубликованный комментарий не редактируется; новые результаты публикуются дополнением.

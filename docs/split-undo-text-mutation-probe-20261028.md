## Структура узлов и предусловия

После Q в этих опытах параграф содержит **один** текстовый узел типа 3 со значением `Qtail`. После ввода X и Undo X MSHTML представляет прежний вид как **два** текстовых узла: первый `Q` или `R`, второй `tail`. После Redo X появляются три узла: первый символ, `X`, `tail`. Это наблюдается и в C0 без DOM-мутации custom unit. Поэтому равный `innerHTML` или `innerText` не означает тождественной структуры узлов.

В первом варианте нового теста ошибочное предположение, что после Q первый узел равен только `Q`, привело к `E_UNEXPECTED` до мутации; снимок `c1/probe-value.tsv` показывает `Qtail` и исходный DOM после Q. Это проверка отказа предусловия и не считается тестом успешной операции. В исправленной пробе исходная операция проверяет единственный узел `Qtail`, затем меняет его в `Rtail`; после Undo X `Do` проверяет фактический первый узел `R`, меняет его на `Q`, а затем обратно. Никакого автоматического объединения узлов нет. Идентичности узлов удерживаются через IUnknown на время процесса, что предотвращает повторное использование адресов, но само удержание является возможным влиянием наблюдателя.

## Матрица последовательности

S0=`tail`, S1=`Qtail`; в C1–C3 S2=`Rtail`, S3=`RXtail`. C0 меняет только внутреннее булево состояние и использует S2=`Qtail`, S3=`QXtail`. Проверена последовательность Undo X → Undo custom → Redo custom → Redo X, затем ещё Undo X → Undo custom → Undo Q. Dirty учитывается отдельно.

| Вариант | Последовательность до Redo X | Узлы и дополнительный unit | Последующий Undo Q | Итог сохранности истории |
|---|---|---|---|---|
| C0: внутреннее состояние | PASS; состояние меняется 1→0→1 | Нативный X остаётся следующим, лишней операции не обнаружено | PASS, `tail` | PASS в данном контроле |
| C1: nodeValue первого проверенного узла | PASS: `Rtail → Qtail → Rtail → RXtail` | Идентичность изменяемого первого узла сохраняется; после Undo custom новый top-level text unit не виден | **FAIL**: ожидается `tail`, остаётся `Qtail`; unit Q исчез из Undo | NO-GO |
| C2: один `IHTMLDOMTextNode2::replaceData` | PASS с теми же текстовыми состояниями | Первый узел сохраняет identity; новый top-level text unit не виден | **FAIL**: остаётся `Qtail` | NO-GO |
| C3: локальный `innerHTML` абзаца | **FAIL** на Redo X: остаётся `Rtail`, X не возвращён | После Undo custom появляется новый отдельный `Действие с текстом` перед ожидающим X; узлы пересоздаются | Не является корректной проверкой Q после сбоя Redo | NO-GO |

Сценарный скрипт печатает `TEXT_HISTORY=FAIL` для C1/C2, поскольку включает дополнительный Undo Q; это не означает, что их Redo X потерпел отказ. Снимки `result` содержат независимые `undoX`, `undoMarker`, `redoMarker`, `redoX`, `undoQ`. На снимках C3 после Q узел identity 1, после исходного `innerHTML` identity 2, после Undo X дополнительно identity 3, после custom Undo новый узел identity 4; для C1/C2 первый узел остаётся identity 1. Равенство снимка текста и разная структура узлов фиксируются отдельно.

## Порядок и первая ошибка

Контрольные точки фиксируют вход в `Do`, DOM до и после мутации, состояние перед и после `Add`, затем внешние снимки после Undo/Redo. `Add(this)` завершался `S_OK`; это не доказывает правильную историю само по себе. При попытке перечисления стеков внутри `Do` обе операции возвращали `0x8000FFFF` (`E_UNEXPECTED`); этот предел наблюдаемости не устранялся. `GetOpenParentState` не является индикатором режима менеджера. Удержанные IUnknown и типы позволяют различить top-level units, но не раскрывают внутренние вызовы MSHTML.

В C3 перед Undo custom Redo содержит X. После Undo custom помимо X и custom виден новый текстовый unit с CLSID `{25336920-03F9-11CF-8FD0-00AA00686F13}`, ID 2262 и отдельной COM-идентичностью; после Redo custom следующий Redo исполняет его, а не X. Первая установленная ошибка — этот выбор unit; текст остаётся `Rtail`, то есть X не возвращён. В C1/C2 до этого этапа порядок и текст правильны; первая наблюдаемая ошибка — следующий Undo Q: менеджер убирает unit ввода из Undo, но `Qtail` не становится `tail`. Отсутствие новой top-level записи не доказывает, что внутренней реакции MSHTML не было.

Нельзя приписать отказ Q исключительно мутации внутри `Do`: C1/C2 также выполняют начальную реальную мутацию Q→R до регистрации custom unit. Нужно отдельно контролировать влияние этой операции и обратных мутаций на нативный unit ввода. Сравнение подтверждает различие API для данного сценария, но не устанавливает общую причинность и не доказывает, что все in-place операции небезопасны.

## Ошибки и непроведённые испытания

Проверен только отказ предусловия до начальной DOM-мутации: `E_UNEXPECTED`, документ после Q не менялся. Отказы при самой DOM-мутации и при `Add` и компенсация после частичного изменения — **NOT RUN**; прежний test-only unit не гарантирует атомарности при ошибке `Add`. Отдельное `Do` на параграфе с единственным текстовым узлом, более сложные абзацы/форматирование/ссылки и структурный Split — **NOT RUN**. Хотя C1/C2 прошли короткую последовательность до Redo X, их предшествующая нативная история повреждена, поэтому условие безопасного взаимодействия для расширенного прототипа не выполнено.

Следующая конкретная гипотеза: провести отдельные контроли начальной мутации и обратных действий с идентификацией именно нативного unit Q, сравнив Undo Q непосредственно после каждого независимого перехода; затем исследовать удерживаемые позиции/диапазоны этого unit без пересоздания всего документа. Если публичные COM-интерфейсы не раскрывают внутреннее состояние, требуется адресная отладочная трасса либо test-only прокси регистрации с проверкой, проходит ли через него MSHTML. Нельзя делать вывод о необходимости глобального менеджера по одному этому эксперименту.

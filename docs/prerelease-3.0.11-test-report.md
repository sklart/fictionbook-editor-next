# Предрелизная проверка 3.0.11 — промежуточный отчёт

### Импорт EPUB при длинных временных и внутренних путях

Импортёр изменён для длинного каталога извлечения и длинных имён ресурсов внутри EPUB: проверка компонентов ZIP сохранена, пути канонизируются до применения расширенного префикса Windows, а длинный XML читается MSXML через `IStream`. При этом обрабатывается случай, когда `GetTempPathW` возвращает резервный каталог вместо существующего длинного `TMP`/`TEMP`. Смена способа чтения проверена отдельно: ранний прототип с передачей префикса строкой переводил даже корректные XML на резервный разбор, поэтому этот вариант не принят. Строковые метки использовались только в диагностической сборке и удалены до итоговой адресной проверки.

На DLL `F3B72C6DDEC76FAE5F2FDAE5A70AF14138531F705F8C43C67A90B13087E58092`, собранной из текущих изменённых исходников Win32 Release/v143 14.44 со строгими предупреждениями, прошли 10 новых сценариев `test-import-epub-long-path.py`, 21 сценарий безопасного ZIP, семь связанных fidelity-сценариев и COM `test-import-epub-v2-runtime.ps1`. Проверены Unicode и пути внутри архива длиннее 260 символов, длинный фактически использованный TEMP, относительное изображение с проверкой байтов, штатный резервный разбор ошибочного XHTML, запрет внешней XML-сущности, закодированный выход за пределы и контролируемая подмена каталога junction. Проверена очистка одноразовых каталогов после успеха и отказа; выходные FB2 прошли независимую XSD. Исходная DLL ранее отказала на двух новых длинных случаях. Для теста TEMP проверяется фактический путь извлечения: первоначальный повтор, прошедший за счёт системного резервного каталога, не считается подтверждением поддержки длинного TEMP.

Это адресный комплект с ранее собранным batch и вспомогательной SVG DLL, не единый релизный SHA. UNC, Windows 7, произвольно длинные пути самого входного/выходного файла и реальный EPUB пользователя не проверены; полный релизный gate и финальный fidelity-корпус не выполнялись. Изменения и новый тест нужно включить в финальную приёмку, не заявляя все варианты длинных путей проверенными.

### Recovery: изменение binary во время сериализации

На диагностическом EXE `0896E6895BA41DBCA6387B379009E99C758CC907869793BB026578F3C4BEFEC0` реальный тестовый legacy-скрипт подменил `GetBinaries`: после штатной сериализации он один раз изменил bytes вложения. При недоступном контрольном binary-снимке выполняется консервативная запись, после успешного получения снимка повтор не создаётся. ## Предварительный анализ recovery binary

В текущих исходниках `TryAutoRecovery` прекращает работу при равенстве m_recovery_generation и m_recovery_saved_generation. При этом фасад `base64data` в BinaryPayloadStore увеличивает собственную revision при изменении байтов (одинаковый массив обрабатывается отдельно), но эта revision не связана непосредственно с поколением recovery. Это согласуется с предыдущей диагностикой устаревшего снимка, но просмотр кода не заменяет воспроизведение на итоговом EXE. Прямое использование одной revision без дополнительных проверок преждевременно: она увеличивается также при Assign и может учитывать действия с элементами, не входящими в текущий документ. Требуются тесты восстановления актуальных байтов, отсутствия лишних записей, отмены/повтора и сохранности истории до изменения production.

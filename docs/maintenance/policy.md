# Политика сопровождения документации

> Тип: Действующая инструкция. Документационная база: FBE Next 3.0.9, `master` / `1ad7c507d1ed`; сверка 19 октября 2026 года.

## Типы документов

**Инструкция** объясняет действующий сценарий. **Спецификация** фиксирует формат/контракт. **План** описывает ещё не выполненную работу. **Отчёт** подтверждает конкретную ревизию и окружение. **Архив** сохраняет историю и не становится описанием текущего поведения без отдельной сверки.

В новой или существенно переработанной инструкции указывайте ревизию содержательной проверки. Не объявляйте весь документ проверенным сегодня только потому, что исправили одну ссылку.

## Единственный основной документ по теме

Описание текущей Shell-интеграции находится в `shell-integration.md`, публичный API — в `scripting-api.md`, карточки — в `script-card-format.md` и `script-cards.md`. Исторические планы и этапные отчёты ссылаются на эти документы, а не дублируют их в конкурирующих редакциях.

Таблицы формата, архитектурные решения, пользовательская инструкция и тестовый checklist могут оставаться разными файлами: объединять их в один монолит не требуется.

## Ссылки и перенос

Используйте относительные ссылки внутри репозитория. Ссылки вида `D:\...` недопустимы. Пути к локальным артефактам `out`, `build`, `tmp` в примерах оформляйте как код, а не как якобы существующий файл GitHub.

При переносе файла исправляйте его исходящие ссылки относительно нового расположения. Для исторического источника, удалённого из текущего дерева, используйте явный permalink на существующую исходную ревизию либо пояснённый кодовый путь, но не выдуманный рабочий URL.

Известные публичные пути допускают маленький файл-указатель. Он должен содержать только статус переноса и ссылки, а не вторую копию текста. Якоря старого документа не гарантируются простым указателем; ссылки с якорями внутри репозитория должны обновляться на новый основной файл.

## История и тестовые доказательства

Не удаляйте baseline, proposals, runtime evidence и Markdown, по которому вычисляется sourceSha256, до проверки реальных потребителей. Не форматируйте такие файлы ради стиля: смена пробелов или EOL меняет хеш.

Для этой реорганизации защищённые входы сохраняются побайтно и по прежним путям. Это устраняет необходимость ломать runtime/hash-контракт только ради перемещения файлов. Промежуточные proposals без потребителей архивируются, а не пересоздаются с выдуманной историей.

## Генерируемые результаты

Подробные HTML/JSON/MD-отчёты аудита пишутся в `out/reports/script-cards`, а не в `docs`. Репозиторий хранит генератор, входные контрольные данные и короткий сопровождаемый итог. Исторические большие отчёты остаются доступны по закреплённой Git-ревизии.

Удаление файла из текущего дерева не уменьшает старые Git-объекты. Переписывание истории и force-push не входят в документационную очистку.

## Релизы

Опубликованное body GitHub Release остаётся источником пользовательских примечаний. Репозиторный конспект должен не противоречить ему, но различие объёма само по себе не ошибка: действующий workflow сохраняет ручные правки существующего release. Отдельные опубликованные RC должны быть явно представлены в индексе.

## Документационные проверки

Локальные ссылки/изображения, существование якорей, запрет ссылок на диск разработчика, отсутствие незаполненных маркеров сборки, JSON-синтаксис и сохранность защищённых исходных байтов. Сеть не требуется для проверки внутренних ссылок. Внешние URL считаются отдельной проверкой и не должны блокировать каждую сборку из-за временной недоступности сайта.

Отдельный статический контроль списка методов API сравнивает справочник с кодовым контрактом. Он не заменяет JScript/MSHTML-runtime, ABI/COM-проверки или содержательную оценку примеров.

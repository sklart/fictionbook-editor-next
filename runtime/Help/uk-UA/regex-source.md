# Довідка з регулярних виразів — Код

Примітка до перекладу: російські слова й речення в контрольних прикладах збережено навмисно. Це тестові дані: регулярні вирази, рядки заміни, пробільні символи та очікувані результати відповідають російській еталонній редакції. Пояснення перекладено; приклади не адаптовано автоматично до української типографіки.

Повний посібник із пошуку та заміни в XML-коді книги FictionBook Editor Next.

Редакція: 2 жовтня 2026 року. Режим «Дизайн» описано в regex-design.md. Ці рецепти стосуються «Коду»; PCRE2-вирази не слід переносити без перевірки.

Примітка до перекладу: вирази, заміни та контрольні зразки не змінено. Російський текст у прикладах залишено навмисно, щоб зберегти точні результати й пробільні символи перевіреної редакції.

## 1. Для чого потрібний пошук у «Коді»

У цьому режимі видно XML-теги, атрибути, посилання, сутності й текст. Це відповідний засіб аудиту FB2: порожні елементи, HTML-теги імпорту, заглушки посилань, незвичні атрибути й залишки конвертації.

Для літературної вичитки звичайних слів часто зручніший «Дизайн». У XML збіг може опинитися в атрибуті, коментарі, CDATA, імені файлу чи двійкових даних. Урахуйте це до заміни.

«Лише пошук і перевірка» означає кандидатів, а не доведену помилку XML чи тексту. Навіть проста заміна пробілів змінює значущий вміст; універсально безпечних замін по довільному XML немає.

## 2. Швидкий початок

Збережіть копію, перейдіть у «Код», відкрийте пошук і ввімкніть регулярні вирази. XML-приклади зазвичай враховують регістр і вимикають «Лише слово цілком». Межі задає сам шаблон.

Для простого порожнього абзацу:

```regex
<p>[ \t]*</p>
```

Знаходить `<p></p>` і `<p>   </p>` на одному фізичному рядку, не `<p>Текст</p>`. Не видаляйте автоматично й не перетворюйте на `<empty-line/>`: структурне призначення може бути різним.

Вставляйте лише шаблон, без `/.../g`, лапок C++ та подвоєних рисок JSON.

## 3. Рушій: Scintilla, а не PCRE2

FBE використовує Scintilla з `SCFIND_REGEXP` та `SCFIND_CXX11REGEX`. У розглянутій збірці це C++-реалізація граматики ECMAScript, не PCRE2 і не всі можливості сучасного JavaScript. [S1, S2]

У Scintilla також є старий базовий механізм з іншими правилами. Старі приклади груп з екранованими дужками не змішуйте з C++11: тут `(слово)` захоплює, `\(слово\)` шукає буквальні дужки.

Unicode у XML не заборонено, але UCP і властивостей PCRE2 немає. Класи залежать від стандартної бібліотеки; `\w` не дорівнює всім літерам усіх мов. Для передбачуваного ASCII використовуйте `[A-Za-z0-9_]`. `[А-Яа-яЁё]` охоплює російські літери, не всю кирилицю.

### 3.1. Головні відмінності від «Дизайну»

| Властивість | Дизайн | Код |
| --- | --- | --- |
| Об’єкт пошуку | Текстове подання книги | XML-код |
| Рушій | PCRE2-16 | Scintilla C++11 |
| UCP і Unicode-властивості | Доступні в PCRE2 | Не підтримані як PCRE2-синтаксис |
| Перевірка назад | З обмеженнями PCRE2 | Не підтримана |
| Перша група в заміні | `$1` або `\1` | `\1` |
| Накреслення при заміні | Команди FBE | Лише XML-текст |
| Пошук через фізичні рядки | Залежить від подання; міжабзацна заміна обмежена | Поточний шлях не підтримує |

## 4. Построчний пошук: найважливіше обмеження

У поточному шляху `MatchOnLines` зіставляє вираз окремо з кожним фізичним рядком. Рядок може бути довгим; перенесення за шириною вікна не створює нового фізичного рядка. [S2]

Наприклад:

```xml
<empty-line/> <empty-line/>
```

та:

```xml
<empty-line/>
<empty-line/>
```

Для XML це може бути те саме сусідство. Для regex FBE перший випадок уміщується в один збіг, другий перетинає межу й недоступний.

`\r\n`, `\n`, `\x0D`, `\x0A`, `\s*` або клас будь-якого символу не знімають обмеження. Рушій не отримує обидва рядки як один фрагмент. Потрібна зміна програмного шляху, а не лише виразу.

Водночас заміна може вставити розрив рядка. Це інша операція, наведена в K28. Не плутайте «знайти між рядками» й «вставити межу після знайденого тексту».

### 4.1. Робота з багаторядковим XML

Для атрибута на окремому рядку часто досить шукати сам атрибут без усього тегу. Відношення між кількома рядками перевіряють структурними засобами, валідатором, скриптом або XML-інструментом.

Не видаляйте всі розриви книги заради одного regex: це зачіпає текст, коментарі, CDATA та читабельність. Спершу визначте, чи потрібне міжрядкове зіставлення.

## 5. Символи й екранування

Звичайний символ шукає себе. Буквальний метасимвол екрануйте зворотною скісною рискою.

| Потрібний текст | Вираз |
| --- | --- |
| Крапка | `\.` |
| Плюс | `\+` |
| Питання | `\?` |
| Зірочка | `\*` |
| Кругла дужка | `\(` або `\)` |
| Число у квадратних дужках | `\[[0-9]+\]` |
| Зворотна скісна риска | `\\` |

`.` означає один символ доступного фрагмента, не буквальну крапку. У UTF-8 фактичну обробку визначають адаптер Scintilla й бібліотека; не вимірюйте emoji за припущенням «одна крапка — один видимий знак».

`\r` і `\n` позначають CR/LF, але не дозволяють построчному пошуку перейти межу. Для пробілів і табуляції використовуйте `[ \t]`.

PCRE2-обрамлення `\Q...\E` не є переносним способом екранувати текст тут. Екрануйте спеціальні символи окремо.

## 6. Класи, діапазони й межі слова

`[abc]` знаходить один символ списку, `[a-z]` — діапазону, `[^abc]` — поза списком. Далі можна повтор: `[0-9]+`.

| Клас | Практичний зміст |
| --- | --- |
| `[0-9]` | ASCII-цифра |
| `[A-Za-z]` | Латинська ASCII-літера |
| `[ \t]` | Звичайний пробіл або табуляція |
| `[^<]` | Доступний символ, крім < |
| `[^"']` | Символ, що не є жодною прямою лапкою |
| `\d`, `\D` | Клас цифр реалізації та заперечення |
| `\s`, `\S` | Пробільний клас та заперечення |
| `\w`, `\W` | Клас слова та заперечення |

Негативний клас не розуміє XML. `[^<]*` зручний для простого тексту між тегами, не повного розбору сутностей, коментарів чи CDATA.

`\b` — межа слова, `\B` — не-межа. Для атрибутів її часто замало: `id` може стояти після двокрапки іншого імені. Надійніше явно перевіряти розділювач: початок рядка, пробіл або табуляцію.

## 7. Якорі й повтори

`^` і `$` у поточному шляху задають фізичні межі рядка. Для лише горизонтальних пробілів:

```regex
^[ \t]+$
```

Видалення знайдених символів залишить порожній рядок: розрив не входив до збігу.

| Квантифікатор | Повтори |
| --- | --- |
| `?` | Нуль або один |
| `*` | Нуль або більше |
| `+` | Один або більше |
| `{3}` | Рівно три |
| `{3,}` | Щонайменше три |
| `{2,5}` | Від двох до п’яти |

C++11 дозволяє ліниві форми `*?` та `+?`. Але для атрибута часто ясніше виключити обмежувальну лапку:

```regex
"[^"\r\n]*"
```

Приклад для подвійних лапок; одинарним потрібна власна гілка.

Не переносіть possessive-квантифікатори, атомарні групи та inline-опції PCRE2.

## 8. Групи, альтернатива й перевірки вперед

Захоплювальна група `( ... )` зберігає фрагмент; `(?: ... )` об’єднує без номера.

Вибір кількох тегів:

```regex
<(?:strong|emphasis)>
```

Числове посилання може зв’язати відкривальний і закривальний теги простого однорядкового фрагмента:

```regex
<(strong|emphasis)>[ \t]*</\1>
```

Воно вимагає однакового імені. Це не перевірка довільної XML-вкладеності.

Позитивне `(?=...)` та негативне `(?!...)` lookahead перевіряють правий контекст без включення до збігу. Межа після імені не дає `<a` збігтися з початком `<author>`.

```regex
<a(?=[ \t>])
```

Для перевірки ліворуч захопіть контекст і поверніть у заміні: lookbehind недоступний. Не копіюйте `(?<=...)` з довідки «Дизайн».

## 9. Заміна в режимі «Код»

FBE використовує `SCI_REPLACETARGETRE`: збіг уже знайдено, а Scintilla розгортає заміну за власними правилами. Це не `std::regex_replace` зі звичайним `$1` і не Design-граматика FBE. [S1, S2]

### 9.1. Посилання на захоплення

| У заміні | Значення |
| --- | --- |
| `\0` | Повний збіг |
| `\1` … `\9` | Відповідні групи |
| `$1` | Не використовувати як групу: тут інший синтаксис |

Знайти:

```regex
\(([0-9]+)\)
```

Замінити:

```text
[\1]
```

Із `(12)` виходить `[12]`. Це доречно лише у відібраному контексті: число в круглих дужках не обов’язково є приміткою.

Долар у Source-заміни не потрібно подвоювати за правилами інших систем. Зворотна скісна риска натомість є керувальним символом.

### 9.2. Керувальні символи в заміні

Перевірений код Scintilla обробляє `\t`, `\n`, `\r` та `\\` як табуляцію, LF, CR і буквальну риску. Це не суперечить відсутності міжрядкового пошуку. [S2]

Для CRLF використовується `\r\n`, для LF — `\n`. Вибір має відповідати документу; не створюйте змішаних закінчень випадково.

`\x{00A0}` не вставляє тут Unicode-символ. Використовуйте справжній NBSP. Design-команди `\U`, `\L`, `\T`, `\S`, `\E`, `\Q` не задають регістру чи накреслення.

### 9.3. Видалення й збереження XML

Порожня заміна видаляє діапазон. Видалення порожнього тегу, атрибута чи посилання може пошкодити документ попри успішний пошук. Структурні рецепти нижче переважно діагностичні.

Перейменування `id` лише в одному місці залишає старі посилання. Для зв’язаних об’єктів використовуйте штатне перейменування, а не незалежні масові заміни.

## 10. Як читати XML-рецепти

XML чутливий до регістру: `<p>` і `<P>` різні. Порядок атрибутів не визначає зміст, можливі одинарні/подвійні лапки й пробіли навколо рівності. Приклади охоплюють звичайні варіанти, доки правило не надто ускладнюється. [S3]

`l:` та `xlink:` — поширені префікси XLink у FB2. Зміст задає `xmlns`, а не саме ім’я префікса. Рецепти з цими формами не гарантують інші: адаптуйте правило й перевірте декларацію.

`[^>]*` часто наближено описує вміст відкривального тегу. Це зручно, але `>` законний в атрибуті. Коментарі й CDATA можуть містити псевдорозмітку. Тому це кандидати для перегляду, не повна XML-валідація чи сліпа перебудова.

Порожній елемент не завжди порушує схему, числова сутність не означає пошкодження. Заглушка, незвичне ім’я чи зовнішнє посилання теж можуть мати законну мету.

## 11. Практичні рецепти FB2/XML

За замовчуванням частини прикладу мають бути на одному фізичному рядку. Якщо шукається весь відкривальний тег, усі перевірювані атрибути також мають бути там. Для пошуку лише атрибута такої вимоги до цілого тегу немає.

### K01. Пробіли наприкінці фізичного рядка

Знайти хвіст звичайних пробілів і табуляції.

Дія: заміна після перевірки.

«Регулярний вираз» — увімкнено; «Лише слово цілком» — вимкнено. «Враховувати регістр» — увімкнено.

Знайти:

```regex
[ \t]+$
```

Контрольний початковий текст:

```text
<p>Текст</p>
```

Той самий контрольний текст із видимими позначеннями:

```text
<p>Текст</p>␠␠␠
```

Тут ␠ означає звичайний пробіл, [TAB] — табуляцію, [NBSP] — U+00A0, [NNBSP] — U+202F, [ZWSP] — U+200B. Це пояснювальний запис; позначення не вставляються до книги.

Замінити: залишити поле цілком порожнім. Слово «порожньо» вводити не потрібно.

Результат заміни:

```text
<p>Текст</p>
```

Контрприклад, який не має знаходитися:

```text
<p>Текст</p>
```


Обмеження та зауваження: Не видаляє розрив. У змішаному XML, CDATA та пробільно чутливих ділянках хвіст може бути текстом. Не вважайте очищення всіх рядків безумовно безпечним.

### K02. Очистити лише пробільний рядок

Видалити пробільні символи рядка без іншого вмісту.

Дія: заміна після перевірки.

«Регулярний вираз» — увімкнено; «Лише слово цілком» — вимкнено. «Враховувати регістр» — увімкнено.

Знайти:

```regex
^[ \t]+$
```

Контрольний початковий текст:

```text

<p>Text</p>
```

Той самий контрольний текст із видимими позначеннями:

```text
␠␠␠[TAB]
<p>Text</p>
```

Тут ␠ означає звичайний пробіл, [TAB] — табуляцію, [NBSP] — U+00A0, [NNBSP] — U+202F, [ZWSP] — U+200B. Це пояснювальний запис; позначення не вставляються до книги.

Замінити: залишити поле цілком порожнім. Слово «порожньо» вводити не потрібно.

Результат заміни:

```text

<p>Text</p>
```

Контрприклад, який не має знаходитися:

```text
<p>Text</p>
```


Обмеження та зауваження: Рядок залишиться порожнім: LF/CRLF не входили до діапазону. Це не видалення всіх порожніх фізичних рядків.

### K03. Пробіл перед закриттям порожнього елемента

Знайти звичайний проміжок перед />.

Дія: заміна після перевірки.

«Регулярний вираз» — увімкнено; «Лише слово цілком» — вимкнено. «Враховувати регістр» — увімкнено.

Знайти:

```regex
[ \t]+/>
```

Контрольний початковий текст:

```text
<empty-line />
```

Замінити:

```text
/>
```

Результат заміни:

```text
<empty-line/>
```

Контрприклад, який не має знаходитися:

```text
<empty-line/>
```


Обмеження та зауваження: XML дозволяє обидві форми. Це косметика, не обов’язкове виправлення. Поєднання може бути у тексті чи коментарі; масову заміну переглядайте.

### K04. Порожній простий абзац

Перевірити пару p без тексту.

Дія: лише пошук і перевірка.

«Регулярний вираз» — увімкнено; «Лише слово цілком» — вимкнено. «Враховувати регістр» — увімкнено.

Знайти:

```regex
<p>[ \t]*</p>
```

Контрольний початковий текст:

```text
<p>  </p><p>Text</p>
```

Очікуваний збіг:

```text
<p>  </p>
```

Контрприклад, який не має знаходитися:

```text
<p>Text</p>
```


Обмеження та зауваження: Не охоплює атрибути, розриви, NBSP-сутність чи вкладений тег. Порожній p та empty-line не автоматично взаємозамінні.

### K05. Два empty-line на одному рядку

Знайти сусідні порожні рядки FB2 на одному фізичному рядку коду.

Дія: лише пошук і перевірка.

«Регулярний вираз» — увімкнено; «Лише слово цілком» — вимкнено. «Враховувати регістр» — увімкнено.

Знайти:

```regex
<empty-line[ \t]*/>[ \t]*<empty-line[ \t]*/>
```

Контрольний початковий текст:

```text
<empty-line/> <empty-line />
```

Очікуваний збіг:

```text
<empty-line/> <empty-line />
```

Контрприклад, який не має знаходитися:

```text
<empty-line/>
<empty-line/>
```


Очікуваний збіг:

```text
&
```

Контрприклад, який не має знаходитися:

```text
<p>A &amp; B</p>
```


Обмеження та зауваження: У CDATA й коментарях & законний, DTD може оголосити інші сутності. Це діагностика, не валідатор. Автоматичне & → &amp; може подвоїти екранування.

### K27. Звичайні внутрішні посилання

Знайти локальну #id-ціль окремо від bookmark.

Дія: лише пошук і перевірка.

«Регулярний вираз» — увімкнено; «Лише слово цілком» — вимкнено. «Враховувати регістр» — увімкнено.

Знайти:

```regex
(?:l|xlink):href[ \t]*=[ \t]*(?:"#[^"]+"|'#[^']+')
```

Контрольний початковий текст:

```text
<a l:href="#note1">1</a>
```

Очікуваний збіг:

```text
l:href="#note1"
```

Контрприклад, який не має знаходитися:

```text
<a l:href="https://example.test">Text</a>
```


Обмеження та зауваження: Показує запис, не доводить існування рівно одного ID. Висячі й дубльовані посилання потребують аналізу документа.

### K28. Рознести два empty-line після однорядкового пошуку

Показати відмінність обмеження пошуку від вставлення розриву заміною.

Дія: одинична контрольована заміна.

«Регулярний вираз» — увімкнено; «Лише слово цілком» — вимкнено. «Враховувати регістр» — увімкнено.

Знайти:

```regex
(<empty-line[ \t]*/>)[ \t]*(<empty-line[ \t]*/>)
```

Контрольний початковий текст:

```text
<empty-line/> <empty-line/>
```

Замінити:

```text
\1\r\n\2
```

Результат заміни:

```text
<empty-line/>
<empty-line/>
```

Контрприклад, який не має знаходитися:

```text
<empty-line/>
<empty-line/>
```


Обмеження та зауваження: Керувальні послідовності Scintilla перетворює на CRLF. Для LF використовуйте \1\n\2. Це не універсальне форматування XML і не ввімкнення багаторядкового пошуку.

### K29. Подвійні пробіли в простому XML-тексті

Знайти фрагмент між тегами з кількома звичайними пробілами.

Дія: лише пошук і перевірка.

«Регулярний вираз» — увімкнено; «Лише слово цілком» — вимкнено. «Враховувати регістр» — увімкнено.

Знайти:

```regex
>[^<]*[ \t]{2,}[^<]*<
```

Контрольний початковий текст:

```text
<p>one  two</p>
```

Очікуваний збіг:

```text
>one  two<
```

Контрприклад, який не має знаходитися:

```text
<p>one two</p>
```


Обмеження та зауваження: Збіг включає кутові розділювачі й увесь фрагмент. Слова зручніше виправляти в «Дизайні». Не замінюйте весь XML-збіг одним пробілом.

## 12. Чому regex не замінює XML-перевірку

Вираз доводить лише локальну схожість із послідовністю символів, не правильність усього документа: вкладеність, схема FB2, простори імен, унікальні ID й наявні цілі потребують окремого аналізу.

Два однакові `id` на різних фізичних рядках не можна надійно виявити одним порівнянням поточного построчного regex. Так само відсутню ціль в іншій частині книги. Для цього потрібні перевірка FBE та структура документа.

Не декодуйте всі XML-сутності: `&lt;` і `&amp;` захищають текст від перетворення на розмітку. Не видаляйте все HTML-подібне з CDATA, коментарів чи цитат коду.

Парність, атрибути й вміст має зберігати операція заміни. Зміна лише відкривального `<strong>` залишає старий закривальний тег. Посилання в прикладі не робить кожну подальшу зміну структурно безпечною.

## 13. Часті помилки

### 13.1. Знаходяться малі теги замість великих

Увімкніть урахування регістру. Для XML це не косметична опція. `[A-Z]` без регістру втрачає сенс перевірки великих тегів.

### 13.2. У заміні буквальний $1

Використовуйте `\1`. Source-заміна йде через Scintilla, не JavaScript чи API з `$1`.

### 13.3. \p, \K або lookbehind не працюють

Це конструкції іншого профілю. Для тексту перейдіть у «Дизайн», для XML перепишіть правило явними класами, захопленням контексту, незахоплювальними групами й lookahead.

### 13.4. Сусідні теги не знаходяться

Перевірте фізичний розрив, пробіл перед `/>`, одинарні лапки, додаткові атрибути й префікс. Текстове сусідство не дорівнює сусідству XML-дерева.

### 13.5. Примітка не знаходиться за іншого порядку атрибутів

«Спершу type, потім href» залежить від порядку. K21 використовує окремі lookahead. Багаторядковий тег усе одно недоступний одному збігу; шукайте атрибут або структуру.

### 13.6. strong/emphasis оголошено помилкою вкладеності

Різні правильні стилі можуть вкладатися. Повтор однакового імені потребує посилання як у K08, не двох незалежних альтернатив.

### 13.7. «Bookmark» знаходить усі примітки

Внутрішнє `#`-посилання ще не bookmark-артефакт. Розділяйте загальний аудит K27 і специфічний префікс K19.

### 13.8. Заміна псує видимий текст

У «Коді» збіги можуть бути в тексті, атрибуті, коментарі чи binary. Скасуйте й звузьте область або правило. Назва «безпечна заміна» не скасовує XML-контексту.

## 14. Обмеження профілю Source

Не використовуйте UCP, властивості PCRE2, lookbehind, сучасні іменовані групи JavaScript/PCRE2, атомарні групи, possessive-квантифікатори, branch reset, підпрограми, PCRE2 verbs, `\K`, `\G` і Design-команди накреслення.

Inline-опції PCRE2 не замінюють прапорці діалогу. Можливості нових браузерних JavaScript не з’являються автоматично в C++11 ECMAScript.

MatchOnLines лишається построчним за будь-якої послідовності розриву в шаблоні. Компіляція іншим рушієм не доводить сумісності FBE.

Для Unicode-слів і складної вичитки є «Дизайн». Для структури — XML/FB2, а не необмежений `.*` для компенсації обмежень.

## 15. Швидкодія й довгі XML-рядки

Короткий вираз не обов’язково швидкий. Необмежені повтори й конкурентні альтернативи можуть гальмувати на великих рядках, особливо коли весь документ чи великий binary лежить в одному рядку.

Починайте з конкретного тегу/атрибута й обмеженого класу, не «будь-яких символів». Окремі діагностичні правила легше перевіряти та скасовувати, ніж пошук усіх можливих помилок разом.

Не зводьте весь XML до одного рядка для обходу MatchOnLines: це змінює документ і не гарантує швидкодії.

## 16. Перевірка після заміни

Порівняйте очікуваний і фактичний діапазон. За груп перевірте лапки, префікси, кутові дужки та закривальні теги. Коментарі, CDATA й binary не мають постраждати.

Перевірте FB2, збережіть і відкрийте після суттєвих змін. Контролюйте «Код ↔ Дизайн», примітки, зображення й текст. Перейменування ID вимагає перевірки об’єкта та всіх посилань.

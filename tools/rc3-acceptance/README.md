# Подготовка адресной приёмки RC3

Workflow `.github/workflows/rc3-isolated-acceptance.yml` запускается при push только в ветку `codex/rc3-acceptance`; все Windows-задания сначала проверяют `RUNNER_ENVIRONMENT=github-hosted` и прекращаются до checkout и тестов на self-hosted runner. Предварительный checkout и итоговая сводка используют Ubuntu runner. Код продукта и подмодули извлекаются по `c4bcb76c3cd03d1dff88fa557aa75261b4ec0461`, а эти диагностические скрипты — из коммита самого workflow. В локальном профиле пользователя ничего запускать не нужно.

Сначала независимо собираются и проверяются по одному случаю ASan и Release. На runner скачивается ProcDump с официального сайта, проверяется подпись Microsoft и сохраняется SHA-256. Для самопроверки он ожидает контрольный x86-процесс с именем `FBE.exe` тем же способом, что и настоящий тест; контрольный процесс дожидается подключения отладчика и намеренно вызывает `__fastfail`. Если ожидаемый процесс и код аварии не получены, адресный тест не начинается. Контрольный minidump проверяется на границы потоков, наличие потоков исключения, системы, модулей и потоков исполнения, код `0xC0000409` и непустой контекст исключения. Это лишь структурная проверка, не полная проверка дампа и не анализ стека. При отсутствии подтверждения подключения к FBE, ошибке или принудительной остановке сборщика, а также при появлении дампа сравнение помечается ошибкой; состояние и пути дампов записываются в `collector-result.json`. Формат фактического журнала ProcDump и коды его выхода ещё предстоит проверить на runner. Настоящий процесс может аварийно завершиться до подключения сборщика; контрольный процесс специально ждёт подключения и не исключает эту гонку. ASan дополнительно использует штатный сбор логов и дампов проекта. При обычной ошибке файлы диагностики сохраняются как артефакты; внезапная потеря runner или исчерпание общего времени задания может помешать выгрузке.

После сравнения запускается UBSan, затем задания release CI; итоговое задание требует успеха всех контуров. Сбой сравнения или UBSan не скрывается, даже если оставшиеся проверки прошли. Полные проверки могут использовать COM-регистрацию и профиль **одноразового runner**. Workflow не содержит задания публикации, не создаёт тег и имеет только `contents: read`.

`case/result.json` описывает только исполнение адресного сценария: его `PASS` не означает успеха сбора аварий или всего сравнения. Необходимо также проверить `collector-result.json` и итоговый статус задания. Классификатор требует записи о процессе FBE внутри временного каталога конкретного случая и его нулевого выхода с тем же PID; непонятный формат журнала считается ошибкой наблюдения. Тесты `test-collector-observation-mocked.ps1` и `test-probe-minidump-mocked.ps1` проверяют подставные данные, не запускают ProcDump и не подтверждают действительные журналы или дампы.

Артефакт сравнения включает диагностические EXE, DLL, PDB и `binary-hashes.json`; набор хешей собирается до адресного случая и остаётся доступен при его ошибке. Это позволяет сохранить точные файлы для анализа, но хеширование само по себе не доказывает соответствие PDB исполняемому файлу. При невозможности выгрузить артефакт задание помечается ошибкой.

Подготовка пока не подтверждает готовность к запуску. YAML прочитан анализатором, вложенные PowerShell-команды разобраны синтаксически, а сценарии проверены с подставными компонентами, включая отказ при изменённых отслеживаемых файлах подмодуля, несовместимой версии VC Tools и восстановление окружения после ошибки. ASan-сценарий сохраняет окружение до импорта Visual Studio; mock-проверка охватывает изменения окружения, ошибку импорта и ошибку harness. Это не проверка actionlint или GitHub Actions. Выполнение на runner, контрольный дамп и доступность зависимостей не проверены. ProcDump загружается по изменяемому адресу: подпись и фактический хеш фиксируются, но заранее закреплённой версии нет.

Существующий checkout `build/rc3-clean-a04a0628` указывает через служебный файл HEAD на целевой SHA. Его `.github/workflows/build.yml` и `ubsan.yml` побайтно совпадают с файлами, на основе которых подготовлен workflow. Все 102 напрямую упомянутых в UBSan и релизных заданиях скрипта присутствуют; после нормализации переводов строк у одного скрипта есть дополнительная проверка происхождения в checkout кандидата. Вложенные `SanitizerCatalog.ps1` и `run-sanitizers.ps1` в этом checkout содержат соответствующую функцию и её вызов. Это проверка имеющихся файлов, а не подтверждение чистоты checkout или состояния индексированных файлов: Git в текущей среде вернул ошибку доступа.

Владелец опубликовал целевой SHA в ветке `codex/prerelease-3.0.11`. Добавлен предварительный checkout кандидата; при неуспехе Windows-проверки не запускаются.

Первый запуск предназначен для push подготовленного коммита в отдельную служебную ветку; workflow не изменяет default branch. Вводить runtime PASS по результатам статических или mock-проверок нельзя.
